Lab 07 • The Vision3
Act 1 • The Concept

So what exactly is a CMDB?

It's Google Maps for your infrastructure.

Google Maps

  • Every road, building, landmark registered
  • Connections between places (roads)
  • "If this road is blocked, what's affected?"
  • Search any location → instant answer

CMDB

  • Every server, app, database registered (CIs)
  • Dependencies between them (relationships)
  • "If this DB is down, what services break?"
  • Search any component → instant answer
ITIL 4: Service Configuration Management ensures accurate, reliable information about CIs and their relationships is available when and where it's needed.

Lab 07 • Dependency Chain9
Act 2 • Discovery!

Wait — did you notice something?

  PostgreSQL Primary  -- runs on --> DB Server 01
  PostgreSQL Replica  -- runs on --> DB Server 01   <-- SAME SERVER!

Both databases run on the same physical server.

If DB Server 01 fails:

  • PostgreSQL Primary goes down → Txn and Stl Services both break
  • PostgreSQL Replica also goes down → no failover possible
  • Result: complete UPI outage with no recovery path
This is a Single Point of Failure (SPOF).
We discovered it by building the CMDB. Without CMDB, this risk is invisible.

This becomes a Problem record in Lab 14 and a Change Request in Lab 15 to separate the databases.

Lab 07 • ITIL Theory13
Act 3 • Keep It Healthy

A stale CMDB is worse than no CMDB

If the data is wrong, people stop trusting it. Then it's back to Slack threads at 2 AM.

ProblemHow to DetectFix
Orphan CIsFilter: relationship count = 0Add dependencies or retire
DuplicatesSort by hostname, spot repeatsMerge records, enable dedup
Stale CIsFilter: updated > 90 days agoVerify with infra team
Missing ownersFilter: support group is emptyEvery CI must have an owner
Rule: Every CI must have: Name + Class + Status + Support Group + at least 1 relationship.
CI status changes in production go through Change Management (Lab 15). Never modify a CI without a change record.
