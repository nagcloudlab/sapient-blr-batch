Lab 07 • The Vision3
Act 1 • The Concept

What is a CMDB?

Google Maps for your infrastructure.

Google Maps

  • Every road, building registered
  • Connections between places
  • "If this road is blocked, what's affected?"
  • Search any location → instant answer

CMDB

  • Every server, app, database = CI
  • Dependencies = Relationships
  • "If this DB is down, what breaks?"
  • Search any component → instant answer
ITIL 4 definition: Service Configuration Management ensures accurate, reliable information about CIs and their relationships is available when and where it's needed.

Lab 07 • Dependencies9
Act 2 • Discovery!

Wait — did you notice?

PostgreSQL Primary  -- runs on --> DB Server 01
PostgreSQL Replica  -- runs on --> DB Server 01   <-- SAME SERVER!

Both databases run on the same physical server.

If DB Server 01 fails:

  • PostgreSQL Primary goes down → Txn + Stl Services break
  • PostgreSQL Replica also goes down → no failover possible
  • Result: complete UPI outage with no recovery path
Single Point of Failure (SPOF). Discovered by building the CMDB.
Without CMDB, this risk is invisible.

This becomes a Problem in Lab 14 and a Change Request in Lab 15.

Lab 07 • ITIL Theory13
Act 3 • Keep It Healthy

A stale CMDB is worse than no CMDB

Wrong data = people stop trusting it = back to Slack at 2 AM.

ProblemHow to detectFix
Orphan CIsFilter: relationship count = 0Add dependencies or retire
DuplicatesSort by hostname, spot repeatsMerge records
Stale CIsFilter: updated > 90 days agoVerify with infra team
Missing ownersFilter: support group = emptyAssign an owner
Every CI must have: Name + Class + Status + Support Group + at least 1 relationship.
In production: CI changes go through Change Management (Lab 15). Never modify without a change record.
