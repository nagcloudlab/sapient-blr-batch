Lab 07 • CMDB4
ServiceNow CMDB

CI Class Hierarchy

Every CI extends the base cmdb_ci table. Child tables add specialized fields.

cmdb_ci (Base)
 ├── cmdb_ci_business_app     ← "UPI Payment Platform"
 ├── cmdb_ci_app_server       ← "UPI Transaction Service" (has: host, port, process)
 ├── cmdb_ci_db_instance      ← "PostgreSQL Primary" (has: DB type, version, DB name)
 ├── cmdb_ci_lb               ← "UPI Production LB"
 ├── cmdb_ci_server           ← "App Server 01" (has: RAM, CPU, OS, disk)
 └── cmdb_ci_appl             ← "Prometheus" (general application)
Why inheritance matters: Choose cmdb_ci_db_instance and you get "TCP Port" and "Database Name" fields automatically. Use generic cmdb_ci and you lose those.

Relationships

CI Relationship Types

Stored in cmdb_rel_ci. Types defined in cmdb_rel_type.

RelationshipQuestion It AnswersUPI Example
Depends onIf B fails, does A break?Txn Service depends on PostgreSQL
Runs onWhere is A hosted?Txn Service runs on App Server 01
ContainsWhat's inside this service?UPI Platform contains all 11 CIs
MonitorsWhat watches this CI?Prometheus monitors Txn Service
A CMDB without relationships is just a spreadsheet. Relationships are what enable impact analysis, blast radius, and auto-assignment.

Lab 07 • CMDB9
Scenario Challenge

DB Server CPU at 97%. Now what?

Thursday 3:47 PM. Grafana shows UPI DB Server 01 CPU at 97% for 12 minutes. PostgreSQL connection pool: 490/500. Settlement batch is stuck.

Using your CMDB, answer:

  • What runs on DB Server 01?
  • If PostgreSQL Primary goes down, which services break?
  • Is the Replica also at risk? (hint: same server!)
  • Who gets paged?
  • What's the blast radius for end users?

SPOF Discovery: Both PostgreSQL instances run on the same server. This becomes a Problem (Lab 14) and a Change Request (Lab 15).

  • Check the History tab — see the audit trail
  • Check the Service Map — how does the visualization change?
  • Change it back to Operational
In production: CI status changes go through Change Management (Lab 15). Never modify a CI without a change record.
Lab 07 • CMDB11
Governance

CMDB Health & Best Practices

CheckWhat to FindHow to Fix
Orphan CIsCIs with 0 relationshipsAdd dependencies or retire
DuplicatesSame server registered twiceMerge records, enable dedup
Stale CIsNot updated in 90+ daysVerify with infra team
Missing ownersNo support groupEvery CI must have an owner
Rule of thumb: Every CI must have: Name + Class + Status + Support Group + at least 1 relationship. If any is missing, the CI is incomplete.

Practice

Exercises

  • 1. Add a CI: Create "UPI Dispute Service" (cmdb_ci_app_server, port 8083). Add: Depends on PostgreSQL, Runs on App Srv 02, Contained by Platform.
  • 2. Maintenance simulation: Mark PostgreSQL Replica as "In Maintenance". What does the Service Map show? Who should be notified?
  • 3. Impact analysis: Manager asks: "We need to patch App Server 01 this weekend. What's the impact?" Write a 3-line impact statement using CMDB.
  • 4. Orphan hunt: Find all CIs with no relationships. How would you detect this automatically in production?
  • 5. Custom field: Add "Compliance Status" (Choice: Compliant/Non-Compliant/Pending) to cmdb_ci. Set values for all UPI CIs.
