Key Terms • Before We Go Further

What do CMDB and CI actually mean?

CI — Configuration Item
Any component that needs to be managed to deliver an IT service. A server, an app, a database, a load balancer, even a piece of software — each one is a CI.

Think of it as: a row in the CMDB spreadsheet — but a very smart one.
CMDB — Configuration Management Database
The central store of all CIs and the relationships between them. It is not just a list — it is a connected map.

Think of it as: the Google Maps of your IT infrastructure. (We will see this on the next slide.)
ITIL 4 definition (plain English version):
Service Configuration Management = making sure you always have accurate, up-to-date information about every component that matters — and how they connect — so that when something breaks you are not starting from zero.

What is a CI Class?

Think of a CI class like a form template. Different things need different fields.

A database CI needs:
Database type (PostgreSQL? MySQL?)
TCP port number
Database instance name
Version
A server CI needs:
RAM (GB)
CPU count
Operating system
Disk size
In simple terms: If you go to a doctor, they give you a different form than if you go to a dentist. Same idea — the class determines which fields are available. Choose the right class or you lose important fields.
Every CI class maps to a database table in ServiceNow. Choosing the right class puts the record in the right table with the right columns.

Act 2 • Step 3

What is a Relationship?

A single CI is just a record in a list. Relationships turn that list into a map.

Without relationships

UPI Transaction Service  (exists)
PostgreSQL Primary       (exists)
App Server 01            (exists)

Q: "If PostgreSQL fails?"
A: "No idea."

With relationships

UPI Txn Service
  |-- depends on -> PostgreSQL
  |-- runs on   -> App Server 01

Q: "If PostgreSQL fails?"
A: "Txn Service breaks."
In simple terms: A contacts list tells you that "Ravi Kumar" exists. A relationship is knowing that Ravi is the DBA for PostgreSQL, who is on-call on Thursdays, and who you should call if the Settlement Service is broken. Without that connection, the contact record is useless at 2 AM.
Lab 07 • Relationships ConceptTeaching Edition
Act 2 • Step 3 (continued)

4 Relationship Types We Use

Each type answers a different question. Use the right one.

TypeQuestion it answersExample
Depends onIf B fails, does A break?Txn Svc depends on PostgreSQL
Runs onWhere is A hosted physically?Txn Svc runs on App Server 01
ContainsWhat components make up this service?UPI Platform contains all 11 CIs
MonitorsWhat tool watches this CI?Prometheus monitors Txn Svc
How to create: Open any CI → scroll to Related Items tab → find CI Relationships → click New → choose type → search for the target CI → Save.
Common mistake: Students often use "Contains" when they mean "Depends on". Use "Contains" only for structural grouping (e.g., a Business App that groups all its child services). Use "Depends on" for runtime dependency.

Jargon Buster — SPOF
Act 2 • Discovery!

What does SPOF mean?

Single Point of Failure

Definition: A single component whose failure causes the entire system to stop working — with no backup or fallover path.
Analogy — the only bridge into town:
Imagine a town that has only one bridge connecting it to the main road. If that bridge is damaged, the town is completely cut off — no alternate route exists. That bridge is a SPOF.

In IT: if your primary database and its replica both run on the same physical server, and that server crashes, you have no failover. That server is a SPOF.
Why does a CMDB find SPOFs?
Because only when you draw the map do you see that two supposedly independent paths actually converge on the same physical component. You cannot spot this from a spreadsheet or a Confluence page.
Lab 07 • SPOF ExplainedTeaching Edition
Act 2 • Discovery!

Wait — did you notice?

PostgreSQL Primary  -- runs on --> DB Server 01
PostgreSQL Replica  -- runs on --> DB Server 01   <-- SAME SERVER!

Both databases run on the same physical server.

If DB Server 01 fails:

  • PostgreSQL Primary goes down → Txn + Stl Services break
  • PostgreSQL Replica also goes down → no failover possible
  • Result: complete UPI outage with no recovery path
Single Point of Failure (SPOF). Discovered by building the CMDB.
Without CMDB, this risk is invisible.

Teaching Note — Governance
Act 3 • Keep It Healthy

Why is stale data dangerous?

Wrong data is not just useless — it actively misleads.

Scenario: Six months after Lab 07, the team migrates PostgreSQL Replica to a new server. They forget to update the CMDB. DB Server 01 is decommissioned.

Next outage: Priya looks up the CMDB. It says Replica is on DB Server 01 (which no longer exists). She wastes 20 minutes trying to reach a server that is gone. She now distrusts the CMDB. She goes back to Slack.

That is the death of a CMDB. It does not break — people just stop using it.
Wrong data > no data (in the bad direction):
No data: "I do not know where the Replica is." You ask someone.
Wrong data: "I know it is on DB Server 01." You act on false information. Potentially for 20 minutes before realising the error.
