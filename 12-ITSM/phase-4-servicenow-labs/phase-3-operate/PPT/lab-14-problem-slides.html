Act 1 • Core Distinction

Incident vs Problem

Incident = Symptom

"The UPI service is failing
 -- restore it NOW!"

Goal:  Restore service ASAP
Focus: Speed
Ask:   WHAT is broken?
When:  Reactive (fire alarm)

Problem = Root Cause

"WHY do UPI payments
 keep failing?"

Goal:  Prevent recurrence
Focus: Depth
Ask:   WHY did it break?
When:  After pattern detected
Analogy: Incident = taking aspirin for a headache. Problem = figuring out you need glasses. Incident management gives you relief. Problem management gives you the cure.

Act 2 • RCA

Root Cause Analysis: the 5 Whys

WHY #1: Why did UPI payments fail?
        --> Transaction failure rate spiked from 0% to 80% instantaneously.

WHY #2: Why did it spike instantaneously (not gradually)?
        --> Something toggled the service into a failure state externally.
            Not resource exhaustion (JVM heap at 45%, latency normal).

WHY #3: Why could something toggle the service externally?
        --> The service exposes /chaos/enable, /chaos/down, /chaos/latency
            endpoints with NO authentication.

WHY #4: Why are chaos endpoints exposed without authentication?
        --> They were added for testing and never secured for production.
            No code review caught the missing auth.

WHY #5: Why did settlements also fail?
        --> No circuit breaker between Settlement and Transaction services.
            Failures cascade with no fallback or timeout.
Root Cause: Unprotected chaos engineering endpoints + missing circuit breaker pattern. Any network-reachable client can trigger a production outage.
Lab 14 • 5 Whys6
Act 2 • Document

Document cause, workaround, and fix

On the Problem form, fill in the Analysis Information tab.

Cause Notes

  • /chaos/* endpoints have no auth
  • Any client can inject failures
  • No circuit breaker between services
  • Failures cascade with no isolation
  • No network segmentation

Workaround

  • curl -X POST .../chaos/disable
  • Restores service in ~30 seconds
  • If unresponsive: docker compose restart
  • Monitor 15 min for stability

Fix Notes (permanent)

  • SECURITY: Spring Security on /chaos/* endpoints (admin role only)
  • RESILIENCE: Resilience4j circuit breaker in Settlement Service
  • RATE LIMIT: Rate limiter on /api/upi/pay
  • MONITORING: Circuit breaker state change alerts
  • NETWORK: Restrict /chaos/* to management network
Permanent fix requires a Change Request — it will be submitted in Lab 15.

Act 2 • Lifecycle

Problem lifecycle

New Problem created from recurring incident pattern. Investigation not started.
Assess Investigation plan documented. Reviewing metrics, logs, code.
RCA Root Cause Analysis in progress. Work notes added with findings.
Known Error Root cause identified. Workaround documented. KEDB article published.
Fix in Progress Change Request submitted. Awaiting CAB approval.
Resolved / Closed Fix deployed and verified. No recurrence over 72 hours.
Key difference from incidents: A Problem stays open as a Known Error until the permanent fix is deployed and verified. It can take weeks. The workaround keeps the service running in the meantime.

Act 3 • Proactive Problem

The SPOF from Lab 07 becomes a Problem

Remember the discovery in Lab 07?

PostgreSQL Primary  -- runs on --> DB Server 01
PostgreSQL Replica  -- runs on --> DB Server 01   <-- SAME SERVER!

The risk

  • Both databases on the same physical server
  • If DB Server 01 fails: no failover possible
  • Complete UPI outage with no recovery path
  • No incidents have happened yet

Proactive Problem

  • Create a Problem before incidents occur
  • "UPI Settlement Service single point of failure"
  • Fix: Deploy 2+ replicas behind load balancer
  • This leads to a Change Request in Lab 15
Proactive Problem Management: Finding risks through CMDB analysis before they cause incidents. This is the highest-maturity ITSM practice.
