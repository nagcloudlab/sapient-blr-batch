Teaching Note • The Gap

What is MTTD — and why does it matter?

In simple terms: MTTD is how long it takes your team to notice that something is broken. Before this lab, that meant waiting for a customer to call and complain.

Without monitoring (before this lab)

T+0s Service starts failing silently
T+5 min First users experience errors
T+15 min Users start calling the helpdesk
T+25 min Agent raises an incident manually
MTTD = ~25 minutes

With monitoring (after this lab)

T+0s Service starts failing
T+60s Prometheus fires alert
T+63s Incident auto-created in ServiceNow
T+63s SLA clock starts immediately
MTTD = ~63 seconds
Why it matters for SLAs: If your P1 SLA requires resolution within 1 hour, every minute of undetected downtime eats into that window. An MTTD of 25 minutes leaves only 35 minutes to fix a P1.

Teaching Note • The Pipeline

How an alert becomes an incident — step by step

In simple terms: Think of it like a fire alarm system. Sensors detect smoke (metrics), the alarm panel decides it is serious enough to call (Prometheus rules), it dials the fire station (AlertManager webhook), the dispatcher logs a case (Snow Bridge), and the case goes into the ticketing system (ServiceNow incident).
Step 1
UPI Service
Exposes metrics at /actuator/prometheus — raw numbers like "how many requests failed"
→
Step 2
Prometheus
Scrapes metrics every 15s. Evaluates rules: "Is failure rate above 50%?" If yes, fires an alert.
→
Step 3
AlertManager
Receives the alert. Deduplicates it (no spam), groups related alerts, then routes it to Snow Bridge via HTTP webhook.
→
Step 4
Snow Bridge
Python service. Translates alert severity to ServiceNow priority. Calls ServiceNow REST API to create incident.
→
Step 5
ServiceNow
Incident created with correct priority, CI attached, assignment group set. SLA clock starts automatically.
Key insight: No human is in this chain until the incident already exists in ServiceNow. The detection and creation are fully automated.

Teaching Note • Deploy

What are we actually deploying?

In simple terms: We are spinning up a miniature version of a real fintech production environment on your laptop using Docker. Seven containers work together the same way real microservices would work in a data centre — but contained, repeatable, and safe to break.

The application layer

  • UPI Transaction Service — the payment processor. Handles pay and status calls. Built in Spring Boot (Java).
  • UPI Settlement Service — handles NPCI reconciliation. Also Spring Boot.
  • Traffic Generator — a Python script that fires ~2 payment requests per second so there is always something to monitor.

The observability layer

  • Prometheus — the metrics database and alerting engine.
  • Grafana — the visual dashboard. Dashboards are auto-provisioned on startup.
  • AlertManager — handles routing, deduplication, and silencing of alerts.
  • Snow Bridge — our custom glue: converts AlertManager webhooks into ServiceNow incidents.

Teaching Note • Chaos Engineering

What is chaos engineering?

In simple terms: Chaos engineering means deliberately breaking things in a controlled way so you can see what happens — before your users find out the hard way. It is like a fire drill: you trigger the alarm on purpose so you know everyone knows what to do when a real fire starts.

Why do we do it?

  • Real production failures are unpredictable — chaos tests whether your monitoring and processes actually work
  • Confirms that alerts fire within the expected time window
  • Confirms that incidents are created with the right priority
  • Confirms that SLA clocks start and the right team is notified

What our chaos script does

  • Option 1: Tell the UPI service to fail 80% of all payment requests
  • Option 2: Tell the service to add 5 seconds of artificial delay to every request
  • Option 3: Shut the service down completely
  • Option 4: Remove all chaos and return to normal
Important: We are not doing anything destructive. We are just flipping a flag inside the running container. The fix is instant — choose option 4.

Teaching Note • Metrics

What each metric means in simple terms

In simple terms: Prometheus collects raw numbers from the services every 15 seconds. The alert rules then ask "is this number outside safe limits?" If yes, an alert fires.
MetricWhat it actually measuresWhy it matters
up Is the service reachable? 1 = yes, 0 = no. The most basic check. If this is 0, the service is completely dead.
upi_transactions_total Count of payment transactions, labelled success or failure. We calculate failure% = failures / (failures + successes). Above 50% is catastrophic for payments.
upi_transaction_duration How long each payment took to process (histogram). p95 means "95% of requests finished within this time". Above 3s means most users are waiting too long.
upi_settlements_total Count of NPCI settlement attempts, labelled settled or failed. Settlement failures mean money is not moving through the network correctly — a regulatory concern.
http_server_requests HTTP response codes from the web layer. 5xx codes are server errors. Above 30% means the HTTP layer itself is broken, not just business logic.
jvm_memory_used How much Java heap memory the service is using. Above 85% usually means a memory leak. The service will crash soon with OutOfMemoryError.

Teaching Note • Key Concepts

MTTD and MTTR — the two numbers that define your ITSM maturity

MTTD
Mean Time To Detect

From: failure starts
To: incident created in ServiceNow

In simple terms: How fast did you notice the house was on fire?

Before this lab: ~25 minutes (someone calls the helpdesk)
After this lab: ~63 seconds (Prometheus fires automatically)
MTTR
Mean Time To Resolve

From: incident created
To: incident resolved and closed

In simple terms: Once you noticed the fire, how fast did you put it out?

MTTR is improved by: run-books, KB articles, auto-assignment, and clear escalation paths — everything from Labs 07-11.
The relationship: SLA resolution time = MTTD + MTTR. A P1 SLA of 1 hour means MTTD + MTTR must together be under 60 minutes. Cutting MTTD from 25 min to 63 seconds gives your engineers an extra 24 minutes to actually fix the problem.
