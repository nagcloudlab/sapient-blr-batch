## Why Overlay Networks?

- Bridge networks are LOCAL to a single Docker host
- In the real world, your application runs across multiple servers
- A frontend on Host A needs to talk to a database on Host B
- Overlay networks solve this — they create a virtual network that spans multiple Docker hosts

```
WITHOUT overlay:
  Host A                          Host B
  +----------------+              +----------------+
  | bridge-net     |              | bridge-net     |
  | [frontend]     |   XXX        | [database]     |
  | 172.17.0.2     | cannot reach | 172.17.0.2     |
  +----------------+              +----------------+
  These are separate, isolated bridge networks with the same IP range!

WITH overlay:
  Host A                          Host B
  +----------------+              +----------------+
  | overlay-net    |              | overlay-net    |
  | [frontend]     |  <-------->  | [database]     |
  | 10.0.1.2       |   VXLAN     | 10.0.1.3       |
  +----------------+  tunnel     +----------------+
  One logical network spanning both hosts!
```

## How Overlay Networks Work

Under the hood, Docker uses **VXLAN (Virtual Extensible LAN)** to create overlay networks:

```
+---------------------------------------------------------------+
|  The VXLAN Tunnel                                              |
|                                                                |
|  Container A on Host 1 sends a packet to Container B on Host 2 |
|                                                                |
|  1. Packet leaves Container A's eth0                           |
|  2. Docker's overlay driver intercepts it                      |
|  3. The original Ethernet frame is ENCAPSULATED inside a       |
|     UDP packet (port 4789) with the destination = Host 2's IP  |
|  4. The UDP packet travels over the physical network           |
|  5. Host 2's Docker receives it, DECAPSULATES the original    |
|     frame, and delivers it to Container B's eth0               |
|                                                                |
|  It is a "tunnel" — a network inside a network                 |
+---------------------------------------------------------------+

```

The containers think they are on the same local network. In reality, their packets are tunneled through UDP port 4789 across the physical network. Docker handles all encapsulation/decapsulation transparently.

## Part 1: Initialize Docker Swarm

- Overlay networks require Docker Swarm mode (even if you only use overlays, not Swarm services)
- Swarm provides the control plane that coordinates overlay networks across hosts

### Step 1.1 — Identify your hosts

```
Host 1 (Manager): IP = <MANAGER_IP>
Host 2 (Worker):  IP = <WORKER_IP>
Host 3 (Worker):  IP = <WORKER3_IP>  (optional)
```

Replace `<MANAGER_IP>`, `<WORKER_IP>`, etc. with your actual IPs throughout this lab.

### Step 1.2 — Initialize the swarm on Host 1

On **Host 1** (this becomes the manager):

```bash
docker swarm init --advertise-addr <MANAGER_IP>
```

- This outputs a `docker swarm join` command with a token
- Copy that entire command — you will need it on the worker nodes

Example output:

```
Swarm initialized: current node is now a manager.

To add a worker to this swarm, run the following command:

    docker swarm join --token SWMTKN-1-xxxxx <MANAGER_IP>:2377
```

### Step 1.3 — Join the workers

On **Host 2** (and Host 3 if available):

```bash
docker swarm join --token SWMTKN-1-xxxxx <MANAGER_IP>:2377
```

### Step 1.4 — Verify the cluster

On **Host 1** (manager):

```bash
docker node ls
```

- You should see all nodes listed with STATUS `Ready`
- One node is marked as `Leader` (the manager)

### Ports that must be open

| Port | Protocol | Purpose |
|------|----------|---------|
| 2377 | TCP | Cluster management and Raft consensus |
| 7946 | TCP + UDP | Node-to-node gossip communication |
| 4789 | UDP | VXLAN overlay network data traffic |

If `docker swarm join` hangs or fails, check that these ports are open between your VMs.

## Part 2: Create an Overlay Network

On **Host 1** (manager):

```bash
docker network create \
  --driver overlay \
  --subnet 10.0.10.0/24 \
  --attachable \
  my-overlay
```

| Flag | Purpose |
|------|---------|
| `--driver overlay` | Use the overlay driver instead of bridge |
| `--subnet 10.0.10.0/24` | Assign a specific subnet (optional but recommended) |
| `--attachable` | Allow standalone containers (not just Swarm services) to join this network |

Verify:

```bash
docker network ls
```

- You should see `my-overlay` with driver `overlay` and scope `swarm`

### Important: --attachable

- By default, overlay networks can only be used by Swarm services (deployed with `docker service create`)
- The `--attachable` flag allows regular `docker run` containers to join the overlay
- This is useful for debugging (running a netshoot container on the overlay to test connectivity)

## Part 3: Run Containers Across Hosts on the Overlay

### Step 3.1 — Start a container on Host 1

On **Host 1**:

```bash
docker run -d --name overlay-host1 --network my-overlay nicolaka/netshoot sleep 3600
```

### Step 3.2 — Start a container on Host 2

On **Host 2**:

```bash
docker run -d --name overlay-host2 --network my-overlay nicolaka/netshoot sleep 3600
```

Note: On the worker node, the overlay network appears automatically when a container joins it. You do not need to create it on each host.

### Step 3.3 — Test cross-host connectivity

On **Host 1**:

```bash
docker exec overlay-host1 ping -c 3 overlay-host2
```

- This ping crosses the physical network through a VXLAN tunnel
- The containers are on different physical machines but appear to be on the same Layer 2 network

### Step 3.4 — Verify DNS works across hosts

```bash
docker exec overlay-host1 nslookup overlay-host2
```

- Docker's DNS resolves `overlay-host2` to its overlay IP (10.0.10.X)
- This works exactly like DNS on a local bridge — but the container is on another host

### Step 3.5 — Check the overlay IP addresses

```bash
docker exec overlay-host1 ip addr
docker exec overlay-host2 ip addr
```

- Each container has TWO network interfaces:
  - `eth0` — connected to the overlay network (10.0.10.X)
  - `eth1` — connected to a local bridge for gateway/internet access

### Verification

```
From overlay-host1 (Host 1):
  ping overlay-host2     --> SUCCESS (cross-host via VXLAN)
  nslookup overlay-host2 --> resolves to 10.0.10.X
  curl http://overlay-host2:80 --> would work if running a web server
```

## Part 4: Swarm Services and Overlay Networking

- While standalone containers with `--attachable` work, the primary use of overlays is with Swarm services
- Swarm services get automatic load balancing, scaling, and service discovery

### Step 4.1 — Create an overlay network for services

On **Host 1** (manager):

```bash
docker network create --driver overlay service-net
```

Note: No `--attachable` needed for Swarm services.

### Step 4.2 — Deploy a replicated service

```bash
docker service create \
  --name web \
  --replicas 3 \
  --network service-net \
  --publish published=8080,target=80 \
  nginx
```

| Flag | Purpose |
|------|---------|
| `--replicas 3` | Run 3 instances of nginx, distributed across the swarm |
| `--network service-net` | Attach all replicas to the overlay network |
| `--publish published=8080,target=80` | Expose port 8080 on EVERY node in the swarm |

### Step 4.3 — Verify service distribution

```bash
docker service ps web
```

- You should see 3 tasks distributed across your nodes
- Each task is a container running on a different host (or the same host if you only have 2 nodes)

### Step 4.4 — Test the service

```bash
# From Host 1
curl http://localhost:8080

# From Host 2
curl http://localhost:8080

# From Host 3 (if available)
curl http://localhost:8080
```

- ALL hosts respond, even if no nginx replica is running on that specific host
- This is called the **routing mesh** (explained in Part 5)

## Part 5: The Ingress Network and Routing Mesh

- When you publish a port with `--publish`, Docker creates a special overlay network called `ingress`
- The ingress network enables the **routing mesh**: every node in the swarm listens on the published port and routes traffic to a container that can handle it

```
                    Client Request
                    http://ANY_NODE:8080
                          |
            +-------------+-------------+
            |             |             |
         Host 1        Host 2        Host 3
         :8080         :8080         :8080
            |             |             |
            v             v             v
      [ingress network - routing mesh]
            |             |             |
            v             v             v
        [nginx-1]     [nginx-2]     [nginx-3]
         (or routes to a host that has a replica)
```

### Inspect the ingress network

```bash
docker network inspect ingress
```

- The ingress network is created automatically when you init the swarm
- Every node is connected to it
- It handles the DNAT rules to forward published ports to service containers

### How the routing mesh works

1. A request arrives at Host 2 on port 8080
2. Host 2 may or may not have an nginx replica
3. If it does: traffic goes directly to the local replica
4. If it does not: the ingress network routes the traffic to a node that DOES have a replica
5. Docker uses IPVS (IP Virtual Server) load balancing under the hood

### Verify IPVS rules

```bash
# On any swarm node
sudo apt-get install -y ipvsadm 2>/dev/null
sudo ipvsadm -L -n
```

- You should see a virtual service for port 8080 with real servers (the container IPs)
- IPVS distributes traffic round-robin across the replicas

## Part 6: Internal Service Discovery (VIP vs DNSRR)

- When a Swarm service is created, Docker assigns it a **Virtual IP (VIP)** on the overlay network
- Other services resolve the service name to this VIP
- The VIP load-balances across all replicas of the service

```
Service "web" has 3 replicas:
  Replica 1: 10.0.1.5
  Replica 2: 10.0.1.6
  Replica 3: 10.0.1.7

VIP for "web": 10.0.1.2

When another service calls "web":
  DNS resolves "web" --> 10.0.1.2 (the VIP)
  VIP load-balances to one of the 3 replicas
```

### Test VIP resolution

```bash
# Create a debug service on the same network
docker service create --name debug --network service-net nicolaka/netshoot sleep 3600

# Wait for it to start
docker service ps debug

# Find which node it landed on, then exec into it
# On the node where debug is running:
CONTAINER_ID=$(docker ps --filter name=debug --format '{{.ID}}')
docker exec -it $CONTAINER_ID bash
```

Inside the debug container:

```bash
# Resolve the "web" service name
nslookup web
# Returns the VIP (e.g., 10.0.1.2)

# Resolve individual tasks
nslookup tasks.web
# Returns ALL replica IPs (10.0.1.5, 10.0.1.6, 10.0.1.7)

# curl the VIP — Docker load-balances across replicas
curl http://web
```

```bash
exit
```

### VIP vs DNS Round Robin (DNSRR)

| Mode | How it works | When to use |
|------|-------------|-------------|
| VIP (default) | DNS returns one virtual IP; IPVS load-balances behind it | Most use cases |
| DNSRR | DNS returns ALL replica IPs directly; client picks one | When you need client-side load balancing or the client caches DNS |

To use DNSRR:

```bash
docker service create \
  --name web-dnsrr \
  --replicas 3 \
  --network service-net \
  --endpoint-mode dnsrr \
  nginx
```

- With DNSRR, `nslookup web-dnsrr` returns 3 IPs (one per replica) instead of a single VIP

## Part 7: Encrypted Overlay Networks

- By default, overlay network data traffic (VXLAN) is NOT encrypted
- Anyone who can sniff the physical network can see the encapsulated packets
- For sensitive data, enable encryption

```bash
docker network create \
  --driver overlay \
  --opt encrypted \
  secure-overlay
```

- The `--opt encrypted` flag enables IPsec encryption on the VXLAN tunnel
- All traffic between containers on this network is encrypted in transit
- There is a performance cost (~10-15% overhead depending on workload)

### When to use encrypted overlays

| Scenario | Encryption needed? |
|----------|-------------------|
| Containers on the same trusted data center network | Probably not |
| Containers crossing the public internet (multi-region) | Yes |
| Handling PCI, HIPAA, or other compliance data | Yes |
| Development and testing environments | No |

### Verify encryption is enabled

```bash
docker network inspect secure-overlay --format '{{.Options}}'
```

- You should see `encrypted:` in the options

## Part 8: Overlay Network Internals

### 8a: The network namespaces

On a swarm node running an overlay container:

```bash
# List Docker's hidden network namespaces
sudo ls /var/run/docker/netns/
```

- You will see namespaces like `1-abc123xyz` and `ingress_sbox`
- These are the overlay network's namespace and the ingress namespace

### 8b: The VXLAN interface

```bash
# Find the VXLAN interface inside the overlay namespace
OVERLAY_NS=$(sudo ls /var/run/docker/netns/ | grep "^1-" | head -1)
sudo nsenter --net=/var/run/docker/netns/$OVERLAY_NS ip link
```

- You should see a `vxlan0` or `vxlan1` interface
- This is the VXLAN tunnel endpoint

### 8c: Capture VXLAN traffic on the physical network

```bash
# Capture UDP port 4789 (VXLAN) on the host's physical interface
sudo tcpdump -i $HOST_IFACE -n udp port 4789 -c 10
```

While that runs, generate cross-host traffic:

```bash
docker exec overlay-host1 ping -c 3 overlay-host2
```

- You will see UDP packets on port 4789 between the two host IPs
- These are the VXLAN-encapsulated packets carrying the container's ping

### 8d: Decode the VXLAN payload

```bash
# Capture with enough bytes to see the inner packet
sudo tcpdump -i $HOST_IFACE -n udp port 4789 -c 5 -X
```

- In the hex dump, you can see the outer IP header (host IPs) and the inner IP header (container IPs)
- The container IPs (10.0.10.X) are encapsulated inside UDP packets between the host IPs

## Part 9: Multi-Service Application on Overlay

Deploy a realistic multi-service stack across the swarm:

```bash
# Create the overlay network
docker network create --driver overlay app-overlay

# Deploy a backend database
docker service create \
  --name postgres \
  --network app-overlay \
  -e POSTGRES_PASSWORD=secret \
  postgres:15

# Deploy a backend API (multiple replicas)
docker service create \
  --name api \
  --replicas 2 \
  --network app-overlay \
  --publish published=3000,target=3000 \
  nginx

# Deploy a frontend (multiple replicas)
docker service create \
  --name frontend \
  --replicas 2 \
  --network app-overlay \
  --publish published=8080,target=80 \
  nginx
```

### Verify the deployment

```bash
# See all services
docker service ls

# See task distribution
docker service ps api
docker service ps frontend

# Verify cross-host connectivity
docker service create --name debug --network app-overlay nicolaka/netshoot sleep 3600

CONTAINER_ID=$(docker ps --filter name=debug --format '{{.ID}}')
docker exec $CONTAINER_ID nslookup postgres
docker exec $CONTAINER_ID nslookup api
docker exec $CONTAINER_ID nslookup frontend
docker exec $CONTAINER_ID nslookup tasks.api
```

### Scale and observe

```bash
# Scale the API to 4 replicas
docker service scale api=4

# Watch the service converge
docker service ps api

# DNS now returns 4 IPs for tasks.api
docker exec $CONTAINER_ID nslookup tasks.api
```

## Troubleshooting

| Problem | Cause | Fix |
|---------|-------|-----|
| `docker swarm join` hangs | Port 2377 blocked between hosts | Open TCP 2377 on the manager's firewall |
| Overlay network created but containers can't communicate | Ports 7946 or 4789 blocked | Open TCP+UDP 7946 and UDP 4789 between all nodes |
| `--attachable` overlay: container starts but no network | Overlay not visible on worker until a container uses it | This is normal; the network is lazy-created on workers |
| Service task stuck in `Pending` | No node has capacity or constraints don't match | Check `docker service ps <name>` for error messages |
| Published port not responding | Routing mesh issue; check if the service has healthy replicas | `docker service ps <name>` and check for `Running` tasks |
| Cross-host ping works but HTTP doesn't | Application-level issue, not network | `docker service logs <name>` to check for app errors |
| VXLAN overhead causing performance issues | Encapsulation adds ~50 bytes per packet | Consider using host networking for latency-sensitive services |
| Encrypted overlay very slow | IPsec encryption overhead | Use encryption only where required by security policy |

## Overlay vs Bridge — When to Use What

| Feature | Bridge | Overlay |
|---------|--------|---------|
| Scope | Single host | Multi-host |
| Requires Swarm | No | Yes |
| Performance | Native speed | ~5-10% overhead (VXLAN encapsulation) |
| DNS | User-defined bridges only | Always |
| Encryption | N/A (local traffic) | Optional (--opt encrypted) |
| Load balancing | None | Built-in (VIP + IPVS) |
| Use case | Development, single-host apps | Production multi-host deployments |

**Challenge 1 — Service failover**

- Deploy a service with 2 replicas across 2 nodes
- Verify you can curl the published port from any node
- Stop Docker on one worker node (`sudo systemctl stop docker`)
- Watch what happens to the service: `docker service ps <name>`
- How long does it take for Swarm to reschedule the replica?
- Restart Docker on the worker and observe the rebalancing

**Challenge 2 — Network partition simulation**

- With an overlay network and containers on two hosts, block port 4789 between them:

```bash
sudo iptables -I INPUT -p udp --dport 4789 -j DROP
```

- Try to ping from container on Host 1 to container on Host 2
- What happens? How quickly does it fail?
- Remove the rule and verify connectivity restores:

```bash
sudo iptables -D INPUT -p udp --dport 4789 -j DROP
```

**Challenge 3 — Compare VIP vs DNSRR latency**

- Create two identical services, one with VIP (default) and one with `--endpoint-mode dnsrr`
- From a debug container, time 100 curl requests to each:

```bash
time for i in $(seq 1 100); do curl -s -o /dev/null http://web-vip; done
time for i in $(seq 1 100); do curl -s -o /dev/null http://web-dnsrr; done
```

- Which is faster? Why?

**Challenge 5 — VXLAN packet dissection**
