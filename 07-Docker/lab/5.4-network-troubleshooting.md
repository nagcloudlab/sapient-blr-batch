## The Troubleshooting Mindset

When Docker networking fails, follow this order:

```
1. Can the container reach itself?            (loopback / localhost)
2. Can the container reach the gateway?       (bridge IP)
3. Can the container reach other containers?  (same network)
4. Can the container reach the host?          (host IP)
5. Can the container reach the internet?      (external IP like 8.8.8.8)
6. Can DNS resolve names?                     (nslookup / dig)
7. Can the application-level protocol work?   (curl / telnet)
```

Each layer builds on the previous one. If step 3 fails, there is no point testing step 5.

## Part 1: tcpdump — Capturing Packets

- tcpdump is the most powerful network debugging tool available
- It captures raw packets on a network interface and displays them in real time
- You can run it inside a container, on the host bridge, or on the host's physical interface

### 1a: Capture inside a container

```bash
docker exec -it debug-box tcpdump -i eth0 -n -c 10
```

| Flag | Meaning |
|------|---------|
| `-i eth0` | Capture on the eth0 interface |
| `-n` | Do not resolve hostnames (faster, less noisy) |
| `-c 10` | Stop after capturing 10 packets |

In another terminal, generate traffic:

```bash
docker exec debug-box curl -s http://app-server
```

You should see TCP packets: SYN, SYN-ACK, ACK (the three-way handshake), followed by HTTP request/response data.

### 1b: Capture on the host bridge

```bash
# Find the bridge interface for debug-net
BRIDGE_IF=$(docker network inspect debug-net --format '{{.Id}}' | cut -c1-12)

# Capture on the bridge — sees ALL traffic between containers on this network
sudo tcpdump -i br-$BRIDGE_IF -n -c 20
```

- This is powerful because you see traffic from ALL containers on the network, not just one
- Useful when you need to see both sides of a conversation

### 1c: Filter by protocol and port

```bash
# HTTP traffic only (port 80)
docker exec -it debug-box tcpdump -i eth0 -n port 80

# DNS queries only (port 53)
docker exec -it debug-box tcpdump -i eth0 -n port 53

# ICMP only (ping)
docker exec -it debug-box tcpdump -i eth0 -n icmp

# Traffic to/from a specific IP
docker exec -it debug-box tcpdump -i eth0 -n host 172.19.0.2

# Combine filters with and/or
docker exec -it debug-box tcpdump -i eth0 -n 'port 80 and host 172.19.0.2'
```

### 1d: Save capture to a file for analysis

```bash
# Capture to a .pcap file inside the container
docker exec -it debug-box tcpdump -i eth0 -n -c 50 -w /tmp/capture.pcap

# Copy it to your host for analysis in Wireshark
docker cp debug-box:/tmp/capture.pcap ./capture.pcap
```

- You can open `capture.pcap` in Wireshark for detailed graphical analysis
- Wireshark can decode HTTP, DNS, TLS, and hundreds of other protocols

### Verification

- You should see the three-way TCP handshake (SYN, SYN-ACK, ACK) when curl connects to nginx
- You should see HTTP GET and HTTP 200 OK in the capture
- DNS queries show the container name being resolved before the connection

## Part 2: DNS Debugging

DNS basics were covered in Lab 5.1 Part 5. This section focuses on **debugging** DNS failures.

### 2a: Essential DNS checks

```bash
# First three commands to run when DNS fails:
docker exec debug-box cat /etc/resolv.conf     # Should show 127.0.0.11
docker exec debug-box nslookup app-server       # Internal DNS
docker exec debug-box nslookup google.com       # External DNS
```

If `resolv.conf` does NOT show `127.0.0.11`, the container is on the default bridge (no DNS) or DNS was overridden with `--dns`.

### 2b: Watch DNS queries with tcpdump

```bash
# Terminal 1: capture DNS traffic
docker exec -it debug-box tcpdump -i eth0 -n port 53

# Terminal 2: trigger a DNS lookup
docker exec debug-box nslookup app-server
```

- You will see a UDP packet to `127.0.0.11:53` and a reply with the IP
- `NXDOMAIN` in the reply means the name does not exist on this network

### 2c: External DNS failures

```bash
docker exec debug-box ping -c 1 8.8.8.8        # Can we reach the internet?
docker exec debug-box nslookup google.com       # Can DNS resolve?
```

- Ping works but nslookup fails → DNS forwarding issue
- Both fail → network connectivity issue (check MASQUERADE rules in Lab 5.2)

## Part 3: Connectivity Debugging

### 3a: Layer-by-layer connectivity test

Run these from inside `debug-box`, stopping at the first failure:

```bash
docker exec -it debug-box bash
```

```bash
# Layer 1: Can I reach myself?
ping -c 1 127.0.0.1

# Layer 2: Can I reach the gateway?
ip route | grep default
# Note the gateway IP, then ping it
ping -c 1 <gateway_ip>

# Layer 3: Can I reach another container on this network?
ping -c 1 app-server

# Layer 4: Can I reach the host?
# Find the host IP from inside the container
ip route | grep default | awk '{print $3}'
# The gateway IP is typically the host's bridge IP

# Layer 5: Can I reach the internet?
ping -c 1 8.8.8.8

# Layer 6: Does DNS work?
nslookup app-server
nslookup google.com

# Layer 7: Does the application protocol work?
curl -v http://app-server
```

```bash
exit
```

### 3b: Testing TCP connectivity with specific ports

```bash
# Test if a specific port is open and responding
docker exec debug-box nc -zv app-server 80

# Test with a timeout (useful for detecting firewalls vs closed ports)
docker exec debug-box nc -zv -w 3 app-server 80

# Test a port that is NOT open
docker exec debug-box nc -zv -w 3 app-server 3306
```

| nc result | Meaning |
|-----------|---------|
| `succeeded` or `open` | Port is open and accepting connections |
| `Connection refused` | Port is closed — nothing is listening there |
| `Connection timed out` | A firewall is dropping packets (no response at all) |

### 3c: Traceroute — see the path

```bash
# Trace the path from debug-box to app-server
docker exec debug-box traceroute app-server

# Trace to an external host — see the gateway hops
docker exec debug-box traceroute -n 8.8.8.8
```

- Within the same bridge network: traceroute shows 1 hop (direct)
- To the internet: traceroute shows the bridge gateway, then the host's route to the internet

## Part 4: Port Mapping Debugging

### 4a: Verify port mapping exists

```bash
docker rm -f web-test 2>/dev/null
docker run -d --name web-test -p 9090:80 nginx

# Check what ports are mapped
docker port web-test

# Verify from the host
curl -s -o /dev/null -w "%{http_code}" http://localhost:9090
```

### 4b: When port mapping fails

Common failure: "port already allocated"

```bash
# Try to start a second container on the same host port
docker run -d --name web-test2 -p 9090:80 nginx
```

- Expected error: `Bind for 0.0.0.0:9090 failed: port is already allocated`
- Fix: Use a different host port or find what is using port 9090

```bash
# Find what is using port 9090 on the host
sudo ss -tlnp | grep 9090

# Or use lsof
sudo lsof -i :9090
```

### 4c: Port mapping works from host but not from other machines

```bash
# This works:
curl http://localhost:9090

# But from another machine on the network, curl http://HOST_IP:9090 fails
```

Diagnose:

```bash
# Check if Docker bound to 0.0.0.0 (all interfaces) or 127.0.0.1 (localhost only)
docker port web-test
# If it shows "127.0.0.1:9090->80/tcp", it is only accessible from localhost

# Check if the host firewall is blocking incoming traffic
sudo iptables -L INPUT -n | grep 9090

# Check if the DNAT rule exists
sudo iptables -t nat -L DOCKER -n | grep 9090
```

### 4d: Port mapping from inside another container

A common misconception: port mapping is for HOST-to-CONTAINER traffic. Containers on the same network should communicate directly, not through port mapping.

```bash
# From inside debug-box, reach app-server directly (NOT through host port)
docker exec debug-box curl http://app-server:80

# This is the correct way — no port mapping needed
# Do NOT use: curl http://host_ip:mapped_port from inside a container
```

## Part 5: Inspecting Network State

### 5a: docker network inspect

```bash
# Full network details including all connected containers and their IPs
docker network inspect debug-net
```

Key fields to check:

| Field | What it tells you |
|-------|-------------------|
| `Driver` | bridge, overlay, host, none, etc. |
| `IPAM.Config.Subnet` | The IP range for this network |
| `IPAM.Config.Gateway` | The gateway IP (bridge interface on host) |
| `Containers` | All containers connected, with their IPs |
| `Options` | Driver-specific options |

### 5b: Formatted output for quick checks

```bash
# List all containers on a network with their IPs
docker network inspect debug-net --format '{{range .Containers}}{{.Name}}: {{.IPv4Address}}{{"\n"}}{{end}}'

# Get just the subnet
docker network inspect debug-net --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'

# Get the gateway
docker network inspect debug-net --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'
```

### 5c: Container network details

```bash
# See all networks a container is connected to
docker inspect app-server --format '{{json .NetworkSettings.Networks}}' | python3 -m json.tool

# Get a container's IP on a specific network
docker inspect app-server --format '{{.NetworkSettings.Networks.debug_net.IPAddress}}'
# Note: network names with hyphens become underscores in the format template
```

### 5d: Check network interfaces on the host

```bash
# List all Docker-related interfaces
ip link show type bridge
ip link show type veth

# Show IP addresses on all interfaces
ip addr show

# Show the routing table
ip route
```

## Part 6: Six Real-World Failure Scenarios

Each scenario: broken setup → diagnose → root cause → fix. Work through them in order.

### Scenario 1: "Cannot resolve container names"

```bash
# Setup — deliberately on default bridge (no --network)
docker rm -f s1-app s1-db 2>/dev/null
docker run -d --name s1-app nginx
docker run -d --name s1-db redis

# Reproduce — DNS fails
docker exec s1-app bash -c "apt-get update -qq && apt-get install -y -qq dnsutils" > /dev/null 2>&1
docker exec s1-app nslookup s1-db

# Diagnose
docker exec s1-app cat /etc/resolv.conf   # NOT 127.0.0.11 — no Docker DNS
```

**Root cause:** Default bridge has no DNS. **Fix:** Use a user-defined network.

```bash
docker rm -f s1-app s1-db
docker network create s1-net
docker run -d --name s1-app --network s1-net nginx
docker run -d --name s1-db --network s1-net redis
docker exec s1-app bash -c "apt-get update -qq && apt-get install -y -qq dnsutils" > /dev/null 2>&1
docker exec s1-app nslookup s1-db   # SUCCESS

# Cleanup
docker rm -f s1-app s1-db && docker network rm s1-net
```

---

### Scenario 2: "Ping works but HTTP connection refused"

```bash
# Setup
docker network create s2-net
docker run -d --name s2-web --network s2-net -p 8888:80 nginx
docker run -d --name s2-client --network s2-net nicolaka/netshoot sleep 3600

# Reproduce — ping works, curl fails
docker exec s2-client ping -c 1 s2-web        # OK
docker exec s2-client curl http://s2-web:8080  # FAILS

# Diagnose — what port is nginx listening on?
docker exec s2-web ss -tlnp                     # Port 80, not 8080
```

**Root cause:** `-p 8888:80` is for HOST access. Container-to-container uses the internal port (80).

```bash
docker exec s2-client curl http://s2-web:80    # SUCCESS

# Cleanup
docker rm -f s2-web s2-client && docker network rm s2-net
```

---

### Scenario 3: "Ping works but DNS fails"

```bash
# Setup — override DNS with bogus server
docker network create s3-net
docker run -d --name s3-box --network s3-net --dns 192.0.2.1 nicolaka/netshoot sleep 3600

# Reproduce
docker exec s3-box ping -c 1 8.8.8.8      # OK (IP works)
docker exec s3-box nslookup google.com     # FAILS

# Diagnose
docker exec s3-box cat /etc/resolv.conf    # Shows 192.0.2.1 instead of 127.0.0.11
```

**Root cause:** `--dns 192.0.2.1` replaced Docker's DNS with an unreachable server.

```bash
docker rm -f s3-box
docker run -d --name s3-box --network s3-net nicolaka/netshoot sleep 3600
docker exec s3-box nslookup google.com     # SUCCESS

# Cleanup
docker rm -f s3-box && docker network rm s3-net
```

---

### Scenario 4: "Containers on different networks cannot communicate"

```bash
# Setup
docker network create s4-frontend
docker network create s4-backend
docker run -d --name s4-web --network s4-frontend nginx
docker run -d --name s4-api --network s4-backend nicolaka/netshoot sleep 3600

# Reproduce
WEB_IP=$(docker inspect --format '{{.NetworkSettings.Networks.s4_frontend.IPAddress}}' s4-web)
docker exec s4-api ping -c 2 $WEB_IP      # FAILS — network unreachable
```

**Root cause:** Different bridge networks are isolated by iptables rules (by design).

```bash
# Fix — connect api to the same network as web
docker network connect s4-frontend s4-api
docker exec s4-api curl -s http://s4-web   # SUCCESS

# Cleanup
docker rm -f s4-web s4-api && docker network rm s4-frontend s4-backend
```

---

### Scenario 5: "Port mapping works locally but not from other machines"

```bash
# Setup — bound to 127.0.0.1 only
docker run -d --name s5-web -p 127.0.0.1:7070:80 nginx

# Reproduce
curl -s http://localhost:7070              # OK
# curl http://HOST_IP:7070               # FAILS from another machine

# Diagnose
docker port s5-web                         # Shows 127.0.0.1:7070 (localhost only)
```

**Root cause:** `-p 127.0.0.1:7070:80` binds to localhost only, not all interfaces.

```bash
docker rm -f s5-web
docker run -d --name s5-web -p 7070:80 nginx
docker port s5-web                         # Shows 0.0.0.0:7070

# Cleanup
docker rm -f s5-web
```

---

### Scenario 6: "Container suddenly lost network connectivity"

```bash
# Setup — simulate accidental disconnect
docker network create s6-net
docker run -d --name s6-app --network s6-net nginx
docker network disconnect s6-net s6-app

# Reproduce
docker exec s6-app bash -c "apt-get update -qq && apt-get install -y -qq iproute2" > /dev/null 2>&1
docker exec s6-app ip addr                 # Only lo — no eth0

# Diagnose
docker inspect s6-app --format '{{json .NetworkSettings.Networks}}'   # Empty
```

**Root cause:** Container was disconnected from its network.

```bash
docker network connect s6-net s6-app
docker exec s6-app ip addr                 # eth0 is back

# Cleanup
docker rm -f s6-app && docker network rm s6-net
```

## Part 7: The Troubleshooting Cheat Sheet

Use this as a quick reference when diagnosing network issues:

```
SYMPTOM                          FIRST COMMAND TO RUN
─────────────────────────────────────────────────────────────
Can't resolve container name  →  docker exec <c> cat /etc/resolv.conf
                                 (Is it 127.0.0.11? Is it user-defined network?)

Can't ping another container  →  docker network inspect <network>
                                 (Are both containers on the same network?)

Can't reach the internet      →  docker exec <c> ping 8.8.8.8
                                 (If fails: check ip_forward and MASQUERADE)

Port mapping not working      →  docker port <container>
                                 sudo iptables -t nat -L DOCKER -n
                                 (Is DNAT rule present?)

Intermittent connectivity     →  docker exec <c> tcpdump -i eth0 -n
                                 (Capture packets during failure)

Connection refused            →  docker exec <target> ss -tlnp
                                 (Is anything listening on that port?)

Connection timeout            →  sudo iptables -L FORWARD -n -v
                                 (Are packets being dropped?)

Everything looks right but    →  docker exec <c> curl -v http://target
  still fails                    (verbose output shows exactly where it stalls)
```

**Challenge 1 — Full packet capture analysis**

- Start two containers on the same network
- Run `tcpdump` on the bridge interface and capture to a `.pcap` file
- From one container, `curl` the other container's nginx
- Stop the capture and copy the file to your host
- Open it in Wireshark (or use `tcpdump -r file.pcap -A` to read it)

**Challenge 2 — DNS round-trip timing**

- Use `dig` to measure DNS resolution time for container names vs external domains:

```bash
docker exec debug-box dig app-server | grep "Query time"
docker exec debug-box dig google.com | grep "Query time"
```

- How much faster is Docker's internal DNS compared to external DNS?
- Why is there a difference?

**Challenge 3 — Build a troubleshooting runbook**

- Create a markdown file documenting your own troubleshooting steps for each of the six scenarios

**Challenge 4 — Break it yourself**
