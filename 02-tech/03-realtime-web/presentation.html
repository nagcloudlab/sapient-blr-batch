Why Real-Time?

The web wasn't designed for real-time. It was designed for documents.

Chat

Slack, Discord, WhatsApp Web — instant message delivery

Live Data

Stock tickers, sports scores, dashboards, IoT sensors

Collaboration

Google Docs, Figma, multiplayer games — shared state

Core Problem: HTTP is request-response. The server can't "push" data to the client on its own.

Protocol Timeline

1996 HTTP/1.0 (RFC 1945)

One request per TCP connection. Open, send, close. Repeat. Simple but wasteful.

1997 HTTP/1.1 (RFC 2068)

Persistent connections (keep-alive), chunked transfer, pipelining. The workhorse of the web for 18+ years.

2011 WebSocket (RFC 6455)

Full-duplex, persistent connection over a single TCP socket. Game changer for real-time.

2015 HTTP/2 (RFC 7540)

Binary framing, multiplexing, header compression, server push. Major performance leap.

1.0

HTTP/1.0 — One Shot, One Kill

  • One request per connection — TCP handshake for every single resource
  • No keep-alive by default — connection closes after response
  • No Host header required — one IP = one website
  • Simple but slow — 10 images = 10 TCP connections
  • No chunked encoding — Content-Length must be known upfront
Client Server | | |--- TCP SYN ----------------->| |<-- TCP SYN-ACK -------------| |--- TCP ACK ----------------->| | | |--- GET /index.html -------->| |<-- 200 OK + body ----------| | | |--- TCP FIN ----------------->| Connection CLOSED | | |--- TCP SYN (new!) ---------->| New connection for | ... | each resource!

HTTP/1.0 Raw Request & Response

Request

GET /hello.html HTTP/1.0
User-Agent: Mozilla/3.0
Accept: text/html

// Connection closes after response
// No Host header - can't do virtual hosting
// No persistent connections

Response

HTTP/1.0 200 OK
Content-Type: text/html
Content-Length: 137

<html>
  <body>Hello World!</body>
</html>

// TCP connection is immediately torn down
// Must reconnect for next resource
Problem: Loading a page with 30 resources = 30 separate TCP handshakes. Each takes 1 RTT (Round Trip Time). Extremely slow on high-latency networks.
1.1

HTTP/1.1 — Keep It Alive

  • Persistent connections — Connection: keep-alive is default!
  • Host header required — enables virtual hosting (many sites per IP)
  • Chunked transfer encoding — stream data without knowing total size
  • Pipelining — send multiple requests without waiting (rarely used)
  • Cache control — ETag, If-Modified-Since, Cache-Control
  • Range requests — resume downloads
Client Server | | |--- TCP Handshake ----------->| | | |--- GET /index.html -------->| |<-- 200 OK -----------------| | | |--- GET /style.css --------->| Same connection! |<-- 200 OK -----------------| | | |--- GET /app.js ------------>| Still same connection! |<-- 200 OK -----------------| | |

HTTP/1.1 Still Has Problems

Head-of-Line Blocking

Requests must be processed in order. A slow response blocks everything behind it on that connection.

GET /big-image.jpg   // Takes 5 seconds
GET /tiny-icon.png   // Waits 5 seconds!
GET /style.css       // Still waiting...

Connection Limits

Browsers limit to 6 connections per domain. Pages with 100+ resources still bottleneck.

Workarounds: domain sharding (img1.cdn.com, img2.cdn.com), sprite sheets, CSS/JS bundling.

Text-Based Headers

Headers are plain text and sent repeatedly. A typical request has 800+ bytes of headers, often the same on every request (cookies, user-agent, etc.).

No Server Push

Server can only respond to requests. It can't proactively send resources it knows the client will need.

2

HTTP/2 — The Multiplexer

  • Binary framing — not text! Frames instead of text messages
  • Multiplexing — multiple streams over ONE connection
  • Header compression — HPACK eliminates redundancy
  • Server push — send resources before they're requested
  • Stream prioritization — critical resources first
  • Backwards compatible — same semantics (GET, POST, headers)
Client Server | | |=== Single TCP Connection ====| | | |-- Stream 1: GET /html ----->| |-- Stream 3: GET /css ------>| All at once! |-- Stream 5: GET /js ------->| | | |<- Stream 3: css data ------| Responses interleaved! |<- Stream 1: html data -----| |<- Stream 5: js data -------| |<- PUSH Stream 2: logo.png | Server push!

HTTP/2 Binary Framing Layer

HTTP/1.1 (Text)

GET /page HTTP/1.1\r\n
Host: example.com\r\n
Accept: text/html\r\n
Cookie: session=abc123def456\r\n
\r\n

// Every header repeated on every request
// Human readable but inefficient
// ~800 bytes of headers per request

HTTP/2 (Binary Frames)

// Frame: [Length(3) | Type(1) | Flags(1) | StreamID(4)]

HEADERS frame (stream 1):
  :method = GET      // pseudo-headers
  :path   = /page
  :scheme = https
  cookie  = [index 42]  // HPACK reference!

// Headers compressed with HPACK
// Reference previous headers by index
// ~20 bytes for repeated headers!
Key insight: HTTP/2 doesn't change what HTTP does (verbs, headers, status codes stay the same). It changes how the data is framed and transported.

HTTP Versions Compared

Feature HTTP/1.0 HTTP/1.1 HTTP/2
Connection New for each request Persistent (keep-alive) Single multiplexed
Parallelism Multiple TCP connections 6 connections per domain Unlimited streams on 1 connection
Header Format Text Text Binary (HPACK compressed)
Head-of-Line Blocking N/A (1 req/conn) Yes (big problem) Solved at HTTP layer*
Server Push No No Yes (PUSH_PROMISE)
Encryption Optional Optional Practically required (TLS)
Virtual Hosting No (no Host header) Yes (Host header) Yes (:authority)

* HTTP/2 still has TCP-level head-of-line blocking. HTTP/3 (QUIC) fixes this with UDP.

Part 2

Real-Time Communication Patterns

How do we get data from server to client without the client asking?

Pattern 1: Short Polling

Client repeatedly asks: "Any new data? Any new data? Any new data?"

  • Simple to implement
  • Wasteful — most responses are "no new data"
  • Delay between updates (polling interval)
  • Server load increases with clients
  • Use case: checking build status, low-frequency updates
// Client-side polling
setInterval(async () => {
  const res = await fetch('/api/messages');
  const data = await res.json();
  updateUI(data);
}, 3000); // Every 3 seconds
Client Server | | |--- GET /messages ---------->| |<-- [] (empty) -------------| | | | ... 3 sec wait ... | | | |--- GET /messages ---------->| |<-- [] (empty) -------------| Wasted! | | | ... 3 sec wait ... | | NEW MSG! | |--- GET /messages ---------->| |<-- [{msg: "Hi!"}] ---------| Got it! | But up to 3s delay! |

Pattern 2: Long Polling

Server holds the request open until new data is available (or timeout).

  • Near real-time delivery
  • Less wasted requests
  • Server holds connections open (resource cost)
  • Reconnection overhead after each response
  • Used by: early Facebook chat, Comet pattern
// Client-side long polling
async function longPoll() {
  const res = await fetch('/api/poll');
  const data = await res.json();
  updateUI(data);
  longPoll(); // Immediately reconnect
}
longPoll();
Client Server | | |--- GET /poll -------------->| | | | ... server waits ... | | ... still waiting ... | | NEW MSG! | |<-- {msg: "Hi!"} -----------| Instant! | | |--- GET /poll -------------->| Reconnect | | | ... server waits ... | | | |<-- 408 Timeout ------------| 30s timeout |--- GET /poll -------------->| Reconnect

Pattern 3: Server-Sent Events (SSE)

Server keeps a single HTTP connection open and streams events to the client.

  • One-way: server → client only
  • Auto-reconnect built into the browser API
  • Event IDs for resuming after disconnect
  • Text-based protocol (simple to debug)
  • Works over HTTP/1.1 (no special server needed)
  • Use case: notifications, live feeds, log streaming
// Client-side SSE
const source = new EventSource('/api/stream');

source.onmessage = (event) => {
  console.log(event.data);
};

source.addEventListener('alert', (e) => {
  showAlert(e.data); // Named events!
});

SSE Wire Format

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: {"temp": 22.5, "time": "10:30"}

data: {"temp": 23.1, "time": "10:31"}

event: alert
data: {"msg": "Temperature spike!"}

id: 42
data: {"temp": 28.7, "time": "10:32"}

retry: 5000
data: reconnect in 5s if dropped
Each message separated by \n\n. Fields: data, event, id, retry.

Pattern 4: WebSockets

Full-duplex, bidirectional communication over a single persistent TCP connection.

  • Two-way: client ↔ server simultaneously
  • Low latency: no HTTP overhead per message
  • Binary & text: send any data format
  • Starts as HTTP: upgrade handshake
  • No auto-reconnect: must handle yourself
  • Use case: chat, gaming, collaborative editing, trading
Client Server | | |--- GET / (Upgrade: websocket)| HTTP Handshake |<-- 101 Switching Protocols | | | |=== WebSocket Connection Open ==| | | |--- "Hello server!" -------->| |<-- "Hello client!" --------| | | |<-- "New notification" -----| Server pushes! |--- "Got it, thanks" ------>| |<-- "Another update" -------| | | | ... hours later ... | Still open!

WebSocket The Upgrade Handshake

Client Request

GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: http://example.com

Server Response

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

After Handshake

// No more HTTP!
// Raw WebSocket frames flow:

Frame: [FIN=1, Opcode=0x1 (text)]
  Payload: "Hello!"

Frame: [FIN=1, Opcode=0x2 (binary)]
  Payload: <binary data>

Frame: [FIN=1, Opcode=0x9 (ping)]
  Payload: heartbeat

Frame: [FIN=1, Opcode=0xA (pong)]
  Payload: heartbeat

Frame: [FIN=1, Opcode=0x8 (close)]
  Payload: 1000 "Normal closure"
Key: The Sec-WebSocket-Accept is computed from the Key + a magic GUID. This proves the server understands WebSocket.

WebSocket Client & Server Code

Browser (Client)

const ws = new WebSocket('ws://localhost:3000');

ws.onopen = () => {
  console.log('Connected!');
  ws.send('Hello Server!');
};

ws.onmessage = (event) => {
  console.log('Received:', event.data);
};

ws.onclose = (event) => {
  console.log('Closed:', event.code);
};

ws.onerror = (error) => {
  console.error('Error:', error);
};

// Send data anytime
ws.send(JSON.stringify({
  type: 'chat',
  message: 'Hi everyone!'
}));

Node.js (Server)

import { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 3000 });

wss.on('connection', (ws) => {
  console.log('New client connected');

  ws.on('message', (data) => {
    console.log('Received:', data);

    // Broadcast to all clients
    wss.clients.forEach((client) => {
      if (client.readyState === WebSocket.OPEN) {
        client.send(data.toString());
      }
    });
  });

  ws.send('Welcome!');
});

console.log('WS Server on :3000');

SSE vs WebSocket — When to Use What?

Feature SSE WebSocket
Direction Server → Client only Bidirectional (full-duplex)
Protocol HTTP (text/event-stream) WS protocol (after HTTP upgrade)
Data format Text only (UTF-8) Text + Binary
Auto-reconnect Built-in (browser handles it) Manual (must implement yourself)
Max connections 6 per domain (HTTP/1.1 limit) No limit (not HTTP)
Firewall/Proxy Works everywhere (it's HTTP!) May be blocked by corporate proxies
Best for Notifications, feeds, dashboards, AI streaming Chat, gaming, trading, collaboration
Complexity Simple (just HTTP) More complex (connection management)
Rule of thumb: If the client only needs to receive → use SSE. If client needs to send AND receive frequently → use WebSocket.

All Patterns at a Glance

Short Polling

Client: "Any data?" → Server: "No"
Client: "Any data?" → Server: "No"
Client: "Any data?" → Server: "Yes! Here."
Simple but wasteful. ~N requests/interval.

Long Polling

Client: "Any data?" → Server: ......
                        Server: "Yes! Here."
Client: "Any data?" → Server: ......
Better latency. 1 open req at a time.

Server-Sent Events

Client: "Stream please" → Server: ---open---
                         ← data: msg1
                         ← data: msg2
Efficient one-way stream. Auto-reconnect.

WebSocket

Client ↔ Server: ---upgrade---
Client → "hello"    ← "welcome"
Client → "data"     ← "broadcast"
Full-duplex. Best for bidirectional.

SSE Node.js Server Implementation

import http from 'http';

const server = http.createServer((req, res) => {
  if (req.url === '/events') {
    // SSE Headers - this is what makes it work!
    res.writeHead(200, {
      'Content-Type':  'text/event-stream',  // Required!
      'Cache-Control': 'no-cache',             // No caching
      'Connection':    'keep-alive',           // Stay open
    });

    // Send a message every 2 seconds
    let id = 0;
    const interval = setInterval(() => {
      const data = { time: new Date().toISOString(), value: Math.random() };
      res.write(`id: ${++id}\n`);           // Event ID for reconnection
      res.write(`data: ${JSON.stringify(data)}\n\n`); // Double newline = end of event
    }, 2000);

    // Clean up when client disconnects
    req.on('close', () => clearInterval(interval));
  }
});

server.listen(3000);

Bonus: HTTP/3 & QUIC

  • Built on QUIC (UDP-based) instead of TCP
  • No TCP head-of-line blocking — lost packet on one stream doesn't block others
  • 0-RTT connection setup — instant reconnection to known servers
  • Built-in encryption — TLS 1.3 integrated into the protocol
  • Connection migration — switch WiFi to cellular without dropping
  • Adopted by Google, Cloudflare, Facebook
TCP + TLS (HTTP/2): |--- TCP SYN --->| 1 RTT |<-- SYN-ACK ---| |--- ACK+TLS --->| 2 RTT |<-- TLS done --| 3 RTT to first data! |--- Request --->| QUIC (HTTP/3): |--- QUIC Hello ->| 1 RTT (or 0-RTT!) |<-- Ready+Data -| to first data! |--- Request ---->|

Best Practices & Gotchas

Do

  • Use SSE for one-way server → client streams
  • Implement heartbeats/ping-pong for WebSocket
  • Handle reconnection with exponential backoff
  • Use JSON for structured messages
  • Add message types/protocols for routing
  • Scale with Redis pub/sub or message queues

Don't

  • Don't use WebSocket when SSE suffices
  • Don't forget to clean up on disconnect
  • Don't send huge payloads over WebSocket
  • Don't ignore connection limits (SSE max 6)
  • Don't use polling if you need < 1s latency
  • Don't trust client messages — always validate
Production tip: Use libraries like Socket.IO (auto-fallback), ws (lightweight), or cloud services (Pusher, Ably, AWS AppSync) instead of raw implementations.

Summary

HTTP Evolution

1.0 → Connection per request
1.1 → Keep-alive, but HOL blocking
2 → Multiplexing, binary, push
3 → QUIC/UDP, 0-RTT

Real-Time Patterns

Polling → Simple, wasteful
Long Polling → Better, still HTTP
SSE → One-way stream, easy
WebSocket → Full-duplex, powerful

Choose Wisely

Dashboard? → SSE
Chat app? → WebSocket
Status check? → Polling
AI streaming? → SSE
