Spring Security Architecture

"It's Filters All The Way Down"

Servlet Filters → DelegatingFilterProxy → FilterChainProxy → SecurityFilterChain → 15+ Filters

← → to navigate

The Big Picture

Spring Security is fundamentally a chain of Servlet Filters

HTTP Request | v +-------------------------------+ | Servlet Container (Tomcat) | | Servlet Filter Chain | | | | [Filter 1] CharEncoding | | [Filter 2] HiddenHttpMethod | | [Filter 3] DelegatingFilterProxy ← bridge | | | | v | | FilterChainProxy | ← Spring Bean | | | | v | | SecurityFilterChain | ← 15+ filters | | | [Filter N] ... | +-------------------------------+ | v DispatcherServlet → Controller → View

Servlet Filters Recap

Servlet Filters intercept HTTP requests before they reach the Servlet. Each filter can:

  • Pass the request to the next filter
  • Block the request (send error/redirect)
  • Modify the request or response
  • Wrap the request/response objects
public interface Filter {
  void doFilter(
    ServletRequest request,
    ServletResponse response,
    FilterChain chain
  );
}

// Typical implementation:
public void doFilter(...) {
  // 1. Pre-processing
  log("Request coming in");

  // 2. Pass to next filter
  chain.doFilter(request, response);

  // 3. Post-processing
  log("Response going out");
}

Layer 1: DelegatingFilterProxy

The bridge between Servlet Container and Spring

Problem

Tomcat manages its own filters. It doesn't know about Spring beans.

Solution

DelegatingFilterProxy is a Servlet Filter that delegates to a Spring bean named springSecurityFilterChain.

Key: Tomcat → DelegatingFilterProxy → FilterChainProxy (Spring bean)
// Simplified:
public class DelegatingFilterProxy
    implements Filter {

  private String targetBeanName =
    "springSecurityFilterChain";

  public void doFilter(...) {
    // Look up Spring bean
    Filter delegate = appContext
      .getBean(targetBeanName);

    // Delegate the work
    delegate.doFilter(req, res, chain);
  }
}
// The bean = FilterChainProxy

Layer 2: FilterChainProxy

The router — picks the right SecurityFilterChain

  • Spring bean: springSecurityFilterChain
  • Contains 1+ SecurityFilterChain instances
  • Matches request URL to the right chain
  • First matching chain wins
  • Single point for debugging
Why? Different URLs need different security: /api/** → JWT, /web/** → form login.
FilterChainProxy | |-- matches /api/** ? | Chain #1 (JWT) | [BearerTokenFilter] | [AuthorizationFilter] | |-- matches /** ? | Chain #2 (Form) | [CsrfFilter] | [UsernamePasswordFilter] | [AuthorizationFilter] | First match wins!

Layer 3: SecurityFilterChain

The chain you configure via HttpSecurity DSL

@Configuration
public class SecurityConfig {

  @Bean
  public SecurityFilterChain filterChain(
      HttpSecurity http) throws Exception {

    http
      .authorizeHttpRequests(a -> a
        .anyRequest().authenticated()
      )
      .formLogin(withDefaults())
      .httpBasic(withDefaults());

    return http.build();
    // build() creates a chain
    // with ~15 filters
  }
}

Flow: Unauthenticated Request

GET /events without logging in

Browser: GET /events v [1-5] DisableEncode → WebAsync → SecurityContext → Headers → CSRF | (pass through for GET) [6] LogoutFilter → Not /logout, skip [7] UsernamePasswordFilter → Not POST /login, skip [8-10] LoginPage, LogoutPage, BasicAuth → skip [11-12] RequestCache, ContextAware → pass through [13] AnonymousAuthFilter → No auth → assigns AnonymousToken v [14] ExceptionTranslationFilter → calls next... [15] AuthorizationFilter → anyRequest().authenticated() AnonymousUser NOT authenticated! → AccessDeniedException v [14] ExceptionTranslationFilter catches it! → Saves /events to RequestCache → Redirects to /login v Browser: 302 → /login

Flow: Login POST

User submits credentials

Browser: POST /login (username=user, password=xxx, _csrf=token) v [5] CsrfFilter → Validates _csrf → VALID [6] LogoutFilter → Not /logout, skip v [7] UsernamePasswordAuthenticationFilter → POST /login matches! INTERCEPT! → Extract username + password → Create UsernamePasswordAuthenticationToken → Call AuthenticationManager.authenticate() v AuthenticationManager v DaoAuthenticationProvider v UserDetailsService.loadUserByUsername("user") v PasswordEncoder.matches(raw, stored) v SUCCESS! → Store Authentication in SecurityContext → Create session → Replay saved /events from RequestCache v Browser: 302 → /events (with JSESSIONID cookie)

SecurityContext & SecurityContextHolder

Where the authenticated user lives

SecurityContextHolder (ThreadLocal) | v SecurityContext | v Authentication +-- principal (UserDetails) +-- credentials (erased after login) +-- authorities (roles/permissions) +-- authenticated (true/false)
ThreadLocal = each request thread has its own copy. Accessible anywhere without passing it.
// Access current user ANYWHERE:

// Option 1: Static
Authentication auth = SecurityContextHolder
  .getContext().getAuthentication();
String user = auth.getName();

// Option 2: @AuthenticationPrincipal
@GetMapping("/profile")
public String profile(
    @AuthenticationPrincipal
    UserDetails user) {
  return user.getUsername();
}

// Option 3: Principal
@GetMapping("/me")
public String me(Principal p) {
  return p.getName();
}

ExceptionTranslationFilter

Converts security exceptions to HTTP responses

// Pseudo-code:
try {
  filterChain.doFilter(req, res);
}
catch (AccessDeniedException ex) {
  if (isAnonymous(auth)) {
    // Not logged in
    requestCache.saveRequest(req);
    entryPoint.commence(req, res);
    // → Redirect to /login
  } else {
    // Logged in, wrong role
    accessDeniedHandler
      .handle(req, res, ex);
    // → 403 Forbidden
  }
}

Not Authenticated

  • Save original URL to session
  • Redirect to /login
  • After login, replay original URL

Authenticated but Forbidden

  • User IS logged in
  • Lacks required role
  • Returns 403 Forbidden
This is why you land on the page you originally tried to visit after login!

Multiple SecurityFilterChains

Different security for different URL patterns

@Configuration
public class SecurityConfig {

  @Bean @Order(1)  // First match wins!
  public SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")           // Only /api/**
      .authorizeHttpRequests(a -> a.anyRequest().authenticated())
      .httpBasic(withDefaults())              // API = HTTP Basic
      .csrf(c -> c.disable());                // No CSRF for APIs
    return http.build();
  }

  @Bean @Order(2)
  public SecurityFilterChain webChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(a -> a.anyRequest().authenticated())
      .formLogin(withDefaults());              // Web = Form login
    return http.build();
  }
}
@Order = priority. securityMatcher() = URL scope. First match wins.

Architecture Summary

Layer 1: Bridge

DelegatingFilterProxy
Servlet → Spring
Auto-registered by Boot

Layer 2: Router

FilterChainProxy
Routes to right chain
Bean: springSecurityFilterChain

Layer 3: Chain

SecurityFilterChain
15+ filters in sequence
Configured via HttpSecurity

Key insight: Each http.formLogin(), http.csrf() adds a specific filter. The DSL builds the chain.

Key Takeaways

Remember

  • Spring Security = Servlet Filter chain
  • DelegatingFilterProxy bridges Tomcat → Spring
  • FilterChainProxy routes to right chain
  • SecurityFilterChain = what you configure
  • SecurityContextHolder = current user (ThreadLocal)
  • ExceptionTranslationFilter handles auth failures

Common Mistakes

  • Forgetting filter order matters
  • Not using debug logging when stuck
  • Thinking formLogin() IS the filter
  • Not understanding @Order
  • Placing custom filters at wrong position
